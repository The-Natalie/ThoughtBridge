## Feature Description

Stand up the complete project skeleton for ThoughtBridge: a `backend/` FastAPI + Pydantic v2 project (layout `api/`, `core/`, `db/`, `ingest/`, `retrieval/`, `llm/`), a `frontend/` React + TypeScript + Vite + Tailwind app with placeholder views and a typed API-client stub, and the full SQLite schema (4 provenance layers plus profiles, explanations, attempts, conversations/turns, FTS5 + vec0 indexes). Establish package managers, test runners, and lint configs, and record the exact commands in AGENTS.md. No behavior beyond what proves the scaffold runs.

## User Story

## Problem Statement

The repo contains workflow tooling, docs, and config but zero application code. Every subsequent deliverable (API wiring, ingestion, retrieval, Q&A, learning, extraction, practice) needs importable packages, a database with the full PRD schema, reproducible installs, and working test/lint commands. This deliverable creates that foundation in one deterministic pass.

## Scope

- In scope: `backend/` project (pyproject, lockfile, app layout, config module, `schema.sql`, connection/init helper, boot/config/db-init tests); `frontend/` project (Vite react-ts template, Tailwind, placeholder views, API-client stub + test); `.gitignore` updates for build artifacts; exact commands recorded in AGENTS.md.
- Out of scope: any API routes/endpoints (deliverable 2+); Meta client module (deliverable 2); ingestion, retrieval, generation, extraction, practice (deliverables 3–5 / later phases); PDF/Word; deployment; seed data.

## Solution Statement

Scaffold with `uv` (installed: 0.10.7) for the backend — `pyproject.toml` + `uv sync` producing `uv.lock` — and `npm create vite` + Tailwind v4's `@tailwindcss/vite` plugin for the frontend. Database access is stdlib `sqlite3` (WAL mode, repository functions, no ORM — FTS5/vec0 virtual tables don't map to ORMs) with schema in idempotent `schema.sql` plus a `schema_version`/`meta` table (no Alembic; pre-release single-user DB is rebuildable). Chunks use INTEGER rowids shared with the vec0 table (`chunks_vec.rowid = chunks.id`); all other entities use TEXT UUIDs. A `fact_chunks` join table makes F-10 independent-support counting queryable.

### Patterns to Follow

No codebase patterns exist yet — these project conventions (AGENTS.md / PRD) are binding for all new code:

**Naming Conventions:**

- Backend `snake_case` modules/functions, `PascalCase` models; frontend `PascalCase.tsx` components, `camelCase.ts` utils; tables plural `snake_case`.

**Error Handling:**

- Config/schema failures raise with actionable messages at startup (fail fast); tests assert failure modes. (Upstream-502 and schema-validation patterns apply to later deliverables.)

**Logging Pattern:**

- stdlib `logging` only, module loggers (`logger = logging.getLogger(__name__)`); no `print()` in backend code. Log DB init summary (tables, vec dim, FTS) at INFO.

**Other Relevant Patterns:**

- Single-writer SQLite: one connection helper, WAL mode, `PRAGMA foreign_keys=ON` every connect, `sqlite_vec.load(conn)` every connect.
- Timestamps TEXT ISO-8601 UTC; JSON columns TEXT with `json.dumps` at write boundaries.
- Frontend API access only through `src/api/client.ts` — views never call `fetch` directly.

### Level 4: Manual Validation

Run each fenced block below as one unit from the repo root. Each block is a subshell: `cd` changes never leak, the server gets a readiness wait (first `uv run` can be slow), and a `trap` guarantees the server is stopped even when a check fails. No job-control (`%1`) references — PIDs only, so the blocks work in non-interactive shells too.

```bash
# Backend boots and serves docs (boot, wait for readiness, check, always stop):
(
  cd backend
  uv run uvicorn app.main:create_app --factory --port 8000 >/tmp/tb_uvicorn.log 2>&1 &
  SRV_PID=$!
  trap 'kill "$SRV_PID" 2>/dev/null; wait "$SRV_PID" 2>/dev/null' EXIT
  for _ in $(seq 1 60); do curl -sf -o /dev/null http://localhost:8000/docs && break; sleep 1; done
  CODE=$(curl -s -o /dev/null -w "%{http_code}" http://localhost:8000/docs); echo "docs:$CODE"; test "$CODE" = "200"
)
```

## NOTES

**Design decisions (with rationale):**

- `uv` over venv+pip: installed (0.10.7), produces `uv.lock` for reproducible hackathon builds/judging, `uv run` removes venv-activation friction. Fallback if `uv sync` fails: `python3.12 -m venv backend/.venv` + `pip install` (record in execution report).
- No ORM (stdlib `sqlite3` + repository functions): FTS5/vec0 virtual tables don't map to ORMs; single-writer scale needs no pooling. WAL + `foreign_keys=ON` every connect.
- No Alembic: pre-release single-user DB; idempotent `schema.sql` + `meta.schema_version` is sufficient and rebuildable. Revisit only if Phase 4 needs migration of a seeded demo DB (unlikely — reseed instead).
- pydantic-settings for config: FastAPI-idiomatic, typed, matches `.env.example` surface exactly.
- Tailwind v4 (`@tailwindcss/vite`, CSS-first): current stable (4.3.x per 2026 sources); no `tailwind.config.js`, no postcss/autoprefixer.
- No react-router: state-based tab skeleton proves the scaffold; routing choice belongs to the deliverable that builds real views.
- vitest node-env client test (no jsdom/testing-library): proves `npm test` meaningfully with zero DOM weight.
- mypy non-strict in validation: catches annotation-level breakage without strict-mode friction at hackathon pace.
- `python-multipart` included now: upload endpoints (deliverable 3) require it; locking early avoids a later lock churn. No upload code in this deliverable.
- `fact_chunks` join table (not a JSON list): makes F-10 "facts left with zero support" counting a query instead of a scan. `chunk_ids` JSON remains the API shape (§10) — translation happens at the repository boundary in deliverable 3+.
- vec0 rowid == `chunks.id` alignment by construction (insert vec row with explicit rowid); enforced by test.

**Trade-offs:**

- Floors over exact pins in `pyproject.toml` (exact versions recorded in `uv.lock`): keeps the plan robust to registry drift between planning and execution; executor must record locked versions in the execution report.
- Frontend `tsc` strictness stays at template default: changing strictness is a later deliberate decision, not scaffold business.

**Assumptions to validate at execution:** registry installs succeed; `BAAI/bge-small-en-v1.5` present in fastembed registry (read-only check) with 384 dims; Vite template + Tailwind v4 install clean on Node 25; `fastapi[standard]` resolves on Python 3.12.
